# 迭代十五批量导入与资料跟踪验收记录（2026-09-24）

## 范围

本轮完成两项不依赖外部服务的 P0 收口工作：按规定规模实测 500 文件批量上传与损坏件隔离；补齐 PRD-INT-001 资料清单的状态、责任对象和备注。OCR、外部 API、Embedding 与供应商接入不在本轮范围。

## 实现

- `scripts/measure_performance_acceptance.py batch-import` 通过真实本机 HTTP 会话发起一次 multipart 请求，不绕过上传接口或工作器。
- 资料清单新增 `status`、`responsible_party`、`notes`，与名称、用途、范围和优先级一起进入统一草稿保存、不可变版本和最终固化。
- 项目编号、风险编号、风险关联和项目数量继续由服务端锁定，前端不能新增、删除、重复或改绑。
- 迁移前草稿读取时仅在响应内补充“待确认 / 待确认 / 空备注”，不回写既有草稿或版本历史；用户再次保存时才创建含新字段的新版本。
- Word/PDF 模板升级到 v3，资料清单以逐项字段表输出状态、责任对象和备注；v1/v2 模板继续保留，既有导出历史不覆盖。

## F01 规定规模实测

设备与运行环境沿用迭代十四：Windows 11，Intel Core i5-13500H，12 核 / 16 逻辑处理器，31.53GB 内存。原始机器可读结果保存在 [`evidence/batch-import-2026-09-24/f01-500-files.json`](evidence/batch-import-2026-09-24/f01-500-files.json)。

| 项目 | 通过标准 | 实测结果 | 结论 |
| --- | --- | --- | --- |
| 上传路径 | 一次真实 multipart 请求接收 500 个 PDF | HTTP 202；500 接受、0 拒绝；上传 5.14 秒 | 通过 |
| 批量容错 | 损坏文件失败但不得中止其他文件 | 480 完成、20 失败；所有失败均为 `PDF_CORRUPT` | 通过 |
| 成果一致性 | 有效件入库，损坏件隔离 | 480 个文档记录、20 个隔离文件 | 通过 |
| 外部访问 | 验收不得依赖外部 OCR 或 API | `external_requests=0` | 通过 |

最后一批任务在处理开始后约 47.06 秒进入终态。该结果证明本机规定规模下的接收、排队、连续处理与隔离闭环，不替代 16GB 目标设备复测。

## 自动化与成品检查

- 后端测试覆盖新字段的默认生成、编辑持久化、旧草稿读取兼容，以及 Word/PDF 文本输出。
- 前端测试覆盖状态、责任对象和备注编辑，并验证完整保存请求。
- Word v3 与 PDF v3 各生成 5 页合成成果，逐页检查标题、表格边界、分页、中文字体和新字段，无截断、重叠或越界。
- 标准 DOCX 渲染器因本机未安装 LibreOffice/`soffice.exe` 无法转换；按既有替代路径使用 Microsoft Word 只读导出 PDF。当前捆绑 Poppler 26.07.0 无法读取同一有效 PDF，最终使用 PDFium 逐页栅格化；`pypdf` 重新打开、页数和文本断言均通过。

## 结论与剩余边界

PRD-UPL-001、PRD-INT-001 和 F01 在当前 32GB Windows 设备上形成可复核闭环。仍需在 16GB 目标设备重复 F01 与性能场景；P05 的外部 OCR 页级检查点强退继续登记为环境受阻。OCR 和外部 API 接入按产品顺序留到最后，不在本轮提前启用。
